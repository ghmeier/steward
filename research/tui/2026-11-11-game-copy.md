# Where the game's player-facing copy lives

## Question

Where is the player-facing text today, and what keeps it from moving into one file that is easy to read and edit?

## Findings

Copy lives in two places.

1. **Content files in `data/*.json`.** These hold the crown's herald, met and missed lines, the desk dispute templates with their option labels, the Archive labels and descriptions, and the peasant names. They already use `{amount}`, `{first}` and `{second}` placeholders. The text is authored next to the numbers it describes, and `contentHash` covers it. **Decision (2026-11-11, user): this text stays in JSON.**
2. **Hardcoded TypeScript strings.** Counts are approximate, from grep.
   - `src/tui/command-line.ts`: about 100 to 150 strings, including parse problems, suggestion descriptions and `NUMBER_HELP`.
   - `src/tui/help-menu.ts`: about 80 to 100 strings of help prose and hint lists.
   - `src/tui/village-panels.ts`: about 50 to 70 strings of panel rows and labels.
   - `src/tui/keys.ts`: about 40 to 60 key hint labels.
   - `src/tui/panels.ts`, `app.ts`, `menu.ts`, `court-menu.ts`, `new-game-menu.ts` and `main.ts`: about 100 strings in total.
   - `src/tui/decree-format.ts`: about 20 to 35 strings, nearly all interpolated.
   - The notice modules: `unlock-notices.ts`, `crown-notices.ts`, `audit-notices.ts` and `starvation-notice.ts`.
   - Core rejection reasons: about 10 in `src/core/illusion.ts`, 2 in `crown.ts` and 3 in `desk.ts`.

### Constraints

- **The core boundary.** `src/core/core-boundary.test.ts` lets core files import only from `src/core/`. Core rejection reasons are player-facing, so the copy module has to live at `src/core/copy.ts`. The text interface can import it from there.
- **Command tokens are not copy.** `command-line.ts` matches suggestion `.text` against what the player types, for example `rest === choice.text`, `word === "owed"` and `next.text === "above"`. Those literals are grammar. Only descriptions, problems and help move.
- **Layout stays in code.** Help rows, petition rows and the resource table set column widths with `padEnd`/`padStart`. The copy file supplies labels, and the call site keeps the padding.
- **Key letters inside prose.** For example, `"The Archive opens. Press a to buy."` names a key that `keys.ts` binds. The copy function should take the key as an argument so the two cannot drift apart.
- **Plurals and lists.** `starvation-notice.ts` builds "a, b and N others" and uses `other${n===1?"":"s"}`. The copy module needs a small plural helper.
- **Formatting helpers live in the text interface.** `plain`, `percent` and `describePolicy` are in `tui/decree-format.ts`. The `formatTicks*` functions and `capitalize` are in `tui/format.ts`. Core cannot import them, so copy functions take already formatted strings or numbers as named arguments.
- **Tests pin wording.** Text is pinned heavily in `panels.test.ts` (about 99 hits), `app.test.ts` (about 68), `command-line.test.ts` (about 23) and `court-menu.test.ts` (about 19). The slim-down plan already flagged this: "every wording change then needs test edits."
- **No snapshot or golden test covers text.** `test/golden.json` holds only a simulation state hash.

### Out of scope

- Developer-facing text: invariant `throw new Error(...)` messages and zod/tuning/save `addIssue` messages.
- `runner/sim.ts` command-line interface output. It is a developer tool.
- `core/commands.ts` forwards `err.message` to the player, which lets invariant error text leak. This is a separate fix.
