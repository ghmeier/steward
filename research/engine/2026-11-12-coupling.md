# Where the code is coupled, and which systems could own their own pieces

## Question

Most feature pull requests touch many files. Is the code tangled, and if so, where are the cuts that would let a change to one system stay in that system? The goal is not one folder per feature. It is to find the systems and modules the code already has, and to separate them so that a change is concise and isolated.

## Summary

1. **The module graph is not tangled.** Value imports in `src/` form no cycles. The one large cycle (20 core files) is made only of `import type { Game }` edges, because every manager receives the whole `Game`. The managers also mostly keep to their own state slice. The spread in pull requests does not come from systems reaching into each other's internals.
2. **The spread comes from about a dozen central lists that every system has to join.** A new system or a new field is declared once in its own file, and then again in a validation schema (`validate.ts`), a tuning schema (`tuning.ts`), the initial state (`game.ts`), the state type and version (`state.ts`), the view (`view.ts`), the save upgrades (`save.ts`), the content file list (`save/content.ts` and `test/helpers.ts`), and in the interface: key bindings, hints, panel slots, help topics, notices and command-line verbs. In the governors core pull request, 13 of its 18 non-test source files gained an entry in one of these lists; only `governors.ts` and `delegates.ts` were purely the feature's own.
3. **Three of those lists hold duplicated knowledge rather than a necessary order, and they are the cheapest wins.** The persisted state is described twice, as hand-written types in each system and as Zod schemas in `validate.ts`. The tuning files are listed twice, in `save/content.ts:11-19` and `test/helpers.ts:16-24`. Each focusable panel is declared in five places across `keys.ts`, `panels.ts` and `village-panels.ts`.
4. **Some coupling is essential and should stay central.** This covers the ordered step phases, the ordered save upgrades, the command schema (one replay protocol), and the cross-system rules of the illusion (an audit touches the illusion, the desk, the crown and the governors). The labor shares pull request (#23) shows what a well-isolated change looks like: 7 non-test source files, all of them the decree or labor system's own.
5. **Copy is a frequently edited file, not a coupling problem.** `copy.ts` imports only types, causes no edits elsewhere, and had no recorded merge conflicts. The real conflict magnets are `src/tui/panels.test.ts` (resolved in 5 merges) and `src/tui/village-panels.ts`, `help-menu.ts` and `view.ts`.

The ranked seams, cheapest payoff first, are: derive the test tuning from the real tuning; let each system own its state type, schema and initial value; let each system own its tuning schema; let each system build its own view slice; and let a panel class own its key, unlock and hints. See "Candidate seams".

Two observations on state ownership. First, each manager touches its own slice, plus `posting.resources` and its own random stream. The exceptions are small: the illusion reads the crown's open demand (`illusion.ts:244`), the crown and the step loop write unlock grants directly instead of through `UnlockManager`, and `view.ts` reads four slices directly. Second, `career.followers` (`state.ts:20`) is never read, and `career.needed` is written by `unlocks.ts:57-62` but never read. These are dead fields, like `career.formerStaff` before #22 removed it.

The illusion is also the de facto treasury: everything that spends coin (unlock purchases, hiring, desk rulings, crown deliveries) goes through `illusion.spend` and `illusion.apparent`. That is a real rule of the game (conjured coin can be spent), but the name hides it.

Cycles. With type imports counted, there is one strongly connected component of 20 core files: every manager imports `type Game`, and `game.ts` imports every manager. With type imports excluded, there are **no cycles at all**. The value-import fan-in leaders are `copy.ts` (21), `realm.ts` (17), `unlocks.ts` (13), `data.ts` (11) and `errors.ts` (11), which are all leaves or near leaves. The type cycle is harmless at runtime. It does mean the import graph cannot show any layering among the managers: any manager can call any other through `this.game`.

Cross-system edges between managers. These are the counts of `this.game.<manager>` uses: desk to illusion 7, illusion to crown 7, economy to delegates 14, view to unlocks 10, view to illusion 5. The densest knot is illusion, crown, desk and governors. That knot is the audit rule itself: the illusion places an audit on the desk, the desk settles it through the illusion, the illusion reports the outcome to the crown, the crown's favor scales the illusion's ceiling and audit timing, and a failed audit dismisses a governor (`illusion.ts:349-352`). This coupling is the design of the game, not an accident of the code.

## Essential versus accidental coupling

### Essential: leave it central

- **Step phase order** (`step.ts:50-59`). Determinism depends on it; one list is the clearest place for it.
- **Save upgrades** (`save.ts:60`). Ordered by version. They import system initializers, which is the right direction.
- **The command schema and its switch** (`commands.ts:15-50`, `:87-139`). The command log is a single replay protocol, and the exhaustive `switch` turns a missing case into a compile error. A per-system registry would scatter the protocol and gain nothing.
- **Condition quantities** (`decree.ts:11-27`, `conditions.ts:7-35`). The switch already is the registry, and the union makes it exhaustive. Each quantity needs a name, a reader and a help line; three short edits is the honest cost.
- **The illusion, desk, crown and governors knot.** These cross-calls are the audit rule.
- **`game.ts` as a composition root.** One field and one constructor line per manager is fine.
- **The golden hash** (`test/golden.json`). Any simulation change must change it; that is its purpose.

### Accidental: worth shrinking

- **The persisted state is described twice.** Each system writes its state type by hand (`CrownState` in `crown.ts`, `DeskState` in `desk.ts`, `Governor` in `delegates.ts`, `FormerGovernor` in `governors.ts`), and `validate.ts` restates every one of them as Zod (`validate.ts:75-170`, `:326-358`). Adding `handedOver` to a former governor in #25 touched `governors.ts`, `validate.ts:103` and `view.ts`. `validate.ts` changed in 9 pull requests. Initial values are split too: the crown and the illusion own theirs (`emptyCrownState`, `emptyIllusionState`), but the desk, the economy and labor are built inline in `game.ts:83-105`.
- **Every tuning schema lives in one file.** `tuning.ts` is 515 lines holding economy, desk, governors, crown, illusion and archive schemas, although each section already has its own data file (`data/crown.json` and so on). Tuning types flow the other way from state: systems import `type DeskTuning` from `tuning.ts`.
- **The tuning file list is written twice.** `save/content.ts:11-19` and `test/helpers.ts:16-24` both list the seven data files, and `test/helpers.ts:29-160` restates the whole `Tuning` shape by hand so that each new section must be added there too.
- **System logic inside `view.ts`.** Precision gating (`view.ts:167-169`, `:241-266`, `:275-286`), filling the crown herald line (`:288-309`) and rendering desk entries (`:311-330`) are each one system's rules. `ViewManager` changed in 10 pull requests, and nearly every change was one system's slice.
- **A panel is declared five times.** `FOCUS_IDS` (`keys.ts:19-26`), `BINDINGS` (`keys.ts:48-62`), `GLOBAL_HINTS` (`keys.ts:176-188`, which repeats each letter and unlock from `BINDINGS`), `PANEL_HINTS` (`keys.ts:191-224`), the slot table (`panels.ts:233-244`) and the `Village` record (`village-panels.ts:527-537`). The view separately keeps `PanelId` and `lockedPanels` (`view.ts:73`, `:268-273`). A panel's key handling lives in its class (for example `b` at `village-panels.ts:521`), while its hint for that key lives in `keys.ts:195`, so the two can drift.
- **Notices are wired one by one.** `app.ts:236-260` calls six notice functions, each with a different signature (`(previous, next)`, `(previous, next, expired)`, `(previous.crown, next.crown, tuning)`, a mutable `knownUnlocks` set), and the promotion notice is written inline. Each new notice adds an import and two lines of glue to `app.ts`.
- **Three large files that hold several systems' interface code.** `command-line.ts` (1015 lines) holds the parsing cursor (`:80-237`), the whole decree grammar (`:239-590`), every other verb (`:591-787`) and the `VERBS` list (`:789-864`). `help-menu.ts` holds all eleven topics (`TOPICS`, `:410-425`). `village-panels.ts` holds all six panels. These files are not coupled in the import sense, but every feature edits them, and they are where merges conflict.
- **Readers of a raw collection.** In #22, readers of `posting.delegates.length` in five files had to change once a delegate could stand for a village. Since #22 these mostly go through `DelegateManager.population` and `peasants`, so this risk has largely been paid down. `projection.ts:35-37` still reads `posting.delegates` directly.

### Suspects that turned out fine

- **`Game` as a God object.** It is a service locator: every manager holds the whole `Game` and can call any sibling. In practice each manager keeps to its own state, and the cross-calls are rules of the game. Replacing it with constructor-injected dependencies would add ceremony without reducing the files a feature touches.
- **`GameView` and `MenuContext` as wide shared types.** Every panel receives the whole `GameView` and `Tuning`, but each reader uses a narrow part of it: the Court menu reads only `view.desk`, the roster reads only `delegates` and `governors`, and the notices read one slice each. Narrowing the parameter types would change many signatures and catch nothing.
- **`GameState`.** It is a plain record composed of per-system slices, with clean ownership. The problem is only that its schema is written apart from its types.
- **The Court menu** (`tui/court-menu.ts`) is already generic over desk kinds, because `view.ts` gives it filled labels and options. `court-menu.ts` did not change when governors added candidates to the desk in #22 and #25.

## Candidate seams

Ranked by payoff over cost. "Model" names an existing pattern to copy.

### 1. Derive the test tuning from the real tuning (tiny cost, removes edits from about half of the pull requests)

`test/helpers.ts` changed in 10 pull requests, mostly to add a new tuning section. Export the file map from `save/content.ts` (`{ village: "village.json", ... }`) and build `fullTuningJson` from it. Write `economyTestTuning` as `{ ...tuning, stepMs: 100, maxResourceValue: 1e300, decrees: {...}, economy: {...}, village: {...}, desk: {...} }`, overriding only the sections whose numbers the economy tests compute by hand. It already passes `archive`, `crown`, `illusion` and `governors` straight through. Also replace the hand-listed posting keys in `src/core/serialize.test.ts:57-76` with a generic key-order reversal.

Files: `save/content.ts`, `test/helpers.ts`, `src/core/serialize.test.ts`. About 30 lines changed.

### 2. Each system owns its state type, schema and initial value (medium cost, high payoff)

Put the Zod schema for a slice next to its hand-written type, checked with `z.ZodType<CrownState>` (the pattern `validate.ts:326` already uses for `PostingState`), so the doc comments on the type survive. Give every slice an initializer next to it. `validate.ts` keeps the generic plain-data scan, the root composition, and the refinements that genuinely span slices (`rosterIssues`, which checks names across the roster and the desk, and `tickBoundIssues`). `game.ts` calls the initializers.

Model: `decree.ts` already owns `decreeSchema` and `validate.ts` imports it; `emptyCrownState` and `emptyIllusionState` already exist.

Root after the change:

```ts
const posting: z.ZodType<PostingState> = z.strictObject({
  postingId: z.string(), seed: uint32, rng: z.record(z.string(), rngStream), resources,
  economy: economyStateSchema, delegates: z.array(delegateSchema), nextDelegateId: positiveCount,
  formerStaff: z.array(formerGovernorSchema), decrees: decreeRecord(true),
  labor: laborStateSchema, desk: deskStateSchema, crown: crownStateSchema, illusion: illusionStateSchema,
}).superRefine(rosterIssues);
```

A new field then touches its system file and, when it changes the save, `state.ts` and an upgrade. Files: `validate.ts`, `game.ts`, `crown.ts`, `illusion.ts`, `desk.ts`, `delegates.ts`, `governors.ts`, `economy.ts`, `labor.ts`. About 200 lines moved, no behavior change; `validate.test.ts` should pass unchanged because `validateState` keeps its contract. The small schema primitives (`count`, `positiveCount`) need one shared home; `errors.ts` or `data.ts` already hold similar helpers.

### 3. Each system owns its tuning schema (medium cost, medium payoff)

Move each section's schema next to its system (`crownTuningSchema` in `crown.ts`, the desk's large schema to `desk.ts` or a `desk-tuning.ts` beside it), export the inferred type from there, and leave `tuning.ts` as the root composition plus the cross-section refinement (`tuning.ts:483-501`, the name pool and promotion checks). Its shared primitives (`nonNegative`, `positive`, `textWithPlaceholders`, `repeatIssues`) stay in `tuning.ts` or move with the state primitives. Do this in the same pass as seam 2, system by system, so each system's pull request moves its state and tuning schemas together.

Files: `tuning.ts`, `crown.ts`, `illusion.ts`, `governors.ts`, `desk.ts`, `economy.ts`, `unlocks.ts` (archive). About 350 lines moved. `tuning.ts` drops from per-feature edits (7 pull requests).

### 4. Each system builds its own view slice (small to medium cost, medium to high payoff)

Move `crownView`, `illusionView`, `governorViews` and `deskEntries`, and their view types, into methods on the managers (`game.crown.view()`, and so on). The precision gating moves with them, into the illusion and governors. `ViewManager.compute` becomes a composition of slices plus the few cross-system lines (the ledger, which combines projection, illusion and the governors' report gap; promotion; growth). Keep `GameView` as one composite type and keep `MenuContext` as is, because readers already read narrow slices.

Files: `view.ts`, `crown.ts`, `illusion.ts`, `governors.ts`, `desk.ts`; the interface keeps importing view types, now from their system files. About 150 lines moved. `view.ts` stops changing for one-system features.

### 5. A panel class owns its key, unlock and hints (small to medium cost, medium payoff)

Give `VillagePanel` (`village-panels.ts:60-81`, already the model of a self-contained panel) three declared fields: its focus key, the unlock it needs, and its hint list. `keys.ts` then derives the focus entries in `BINDINGS`, the panel rows of `GLOBAL_HINTS`, `FOCUS_IDS` order and `PANEL_HINTS` from the `Village` record. Global keys that are not panels (`:`, `?`, `n`, `s`, `q`, and the arrows) stay in `keys.ts`. The slot layout in `panels.ts:233-244` can stay a short table, since row placement is a layout decision. This also puts the hint for `b` next to the code that handles `b`.

Files: `keys.ts`, `village-panels.ts`, `panels.ts`, and `help-menu.ts` (`keysLines`). Watch the import direction: `keys.ts` currently has no dependency on panels, so the derivation should live where the `Village` is built rather than make `keys.ts` import `village-panels.ts`.

### 6. Notices as one ordered list with one signature (small cost, small to medium payoff)

Define `type Notice = (previous: GameView, next: GameView, frame: { tuning: Tuning; expired: readonly string[] }) => string | null`, and keep one ordered array (the order is a priority, since the last notice wins). Rewrite the unlock notice to compare `previous.unlocks` with `next.unlocks` instead of mutating a set, and move the inline promotion notice into the list. A new notice is then one file and one array entry.

Files: `app.ts`, the six notice modules, and their tests. About 60 lines.

### 7. Split the decree grammar out of the command line (small cost, payoff in merge conflicts only)

Move `parseDecreeVerb` and its helpers (`command-line.ts:239-590`) into their own module next to `decree-format.ts`, leaving the cursor, `VERBS` and rendering in `command-line.ts`. Keep `VERBS` one central ordered list: it is what the player sees as suggestions, in order, and a registration mechanism would only hide that. The cursor class has to be exported for the grammar to use it.

Files: `command-line.ts`, one new file. Pure move, about 350 lines.

### Seams not recommended

- **Per-system command registration.** See "Essential". The command schema is the replay protocol.
- **A quantity registry.** The `switch` in `conditions.ts` is already that registry.
- **A plugin interface for desk kinds.** The desk switches on kind in five places (`desk.ts:184-189`, `:277-283`, `:290-301`, `:343-358`, `:385-391`), and two of the five kinds belong to other systems (the audit to the illusion, the candidate to governors). A `Record<DeskKind, handler>` contributed by each system would remove those switches, but with five kinds it adds an interface and indirection for little gain. Revisit if a third system needs a desk kind.
- **Splitting `help-menu.ts` per topic.** Each topic already is a function, and adding a topic is one entry in `TOPICS`. A split would reduce conflicts somewhat but add eleven small files; it is not worth it unless help conflicts keep recurring after seams 5 and 6.
- **Narrower panel parameter types**, and **breaking up `Game`.** See "Suspects that turned out fine".

## Copy

`copy.ts` was touched by all four feature pull requests since it was created (#20, #21, #24, #25), plus the three migration pull requests. By the evidence, that is frequent editing rather than coupling.

- It is a leaf. It imports only types from `realm.ts`, so it cannot create a dependency between systems, and no edit to it has forced an edit anywhere else.
- No merge recorded a conflict in it. Sections are keyed by area, and pull requests append to their own sections, as the copy plan intended.
- The test `copy.test.ts` walks the whole object to check that every template renders, which depends on there being one object.

It does have two real costs. First, the rule that copy takes already formatted values, combined with core rejection reasons living in copy, pulled number formatting into core (`core/amount.ts`, added in #24). That is a one-time cost and the result is reasonable. Second, one feature's wording is spread across several sections organized by screen: governor wording sits in `copy.governors`, `copy.notices.governor*`, `copy.help.governors`, `copy.commandLine.quantityHelp.candidates` and `copy.village`. That is the writer's axis (one screen at a time), which is what the consolidation chose on purpose.

If each system owned its wording (for example a `crown-copy.ts` per system), a feature pull request would edit its own copy file instead of the shared one. That would move one file from category (b) to category (a) per pull request, and would cost the single file a writer reads, plus an aggregator for `copy.test.ts`. Since the shared file causes no conflicts and no incidental edits, the trade does not pay. Keep `copy.ts` as it is.

## Tests

Tests are coupled in the same way as the code, and in two places more so.

- **`src/tui/panels.test.ts`** (1110 lines, changed in 14 pull requests, resolved in 5 merges) drives every panel through `createPanels` and a test renderer. It is the largest conflict magnet in the repository. Because `VillagePanel` exposes `body(context, size, focused)` and `key(key, context)`, most per-panel cases could test the panel object directly, in a test file per panel or per pair of panels, leaving `panels.test.ts` for layout, the bar and focus. This pairs naturally with seam 5.
- **`test/helpers.ts`** (changed in 10 pull requests) restates the tuning file list and the whole tuning shape. Seam 1 fixes this.
- **`src/core/serialize.test.ts:57-76`** lists every posting key by hand to build a reordered copy; a generic reversal removes it from future edits.
- **`src/core/validate.test.ts`** (8 pull requests) changes with `validate.ts`. After seam 2 it should change less, though new per-slice schema tests would naturally sit in each system's test file.
- **`src/tui/app.test.ts`** (10 pull requests) exercises the whole app, so notice and key changes reach it. Seam 6 reduces this a little.
- **`test/golden.json`** changes whenever the simulation changes. That is essential and correct.
- System tests in core (`crown.test.ts`, `governors.test.ts`, `favor.test.ts`, `precision.test.ts`) are already well isolated: each new system brought its own test file, and they share only `test/helpers.ts`.
